Protocole du port COM

Piloter S3-KBD depuis un script, un automate ou un terminal : une ligne JSON par commande, une ligne JSON par réponse. C'est le même protocole qu'en Bluetooth et en Wi-Fi ; cette page détaille chaque commande et tout ce qui est propre au port série.

L'essentiel

Chaque ligne envoyée au module est un objet JSON terminé par une fin de ligne (CR, LF ou CRLF). Le module répond, quand il a quelque chose à dire, par des objets JSON sur des lignes distinctes, terminées par CR LF. Les automates peuvent aussi encadrer chaque commande par STX et ETX. Dans les exemples, → est envoyé par l'hôte, ← est reçu du module.

Échange type
→ {"t":"txt","v":"Bonjour, café à 5 € !"}
← {"id":0,"st":"busy"}
← {"id":0,"st":"ready"}
→ {"t":"char","v":"s","m":1}
→ {"t":"ping","n":1}
← {"id":0,"ev":"pong","n":1}

La deuxième commande (Ctrl+S) ne produit aucune réponse : une frappe réussie n'est pas acquittée. Le ping final sert de barrière : son pong n'arrive qu'une fois toutes les commandes précédentes exécutées (voir Réponses).

Activer le port COM

En sortie d'usine, le port COM est désactivé : un module neuf ne se présente que comme un clavier et une souris. Pour l'activer :

  • depuis l'application : Réglages ⚙️ → Fonctions → Port COM (série), puis Enregistrer & redémarrer ;
  • ou par le Bluetooth / le Wi-Fi, avec la commande {"t":"cfg","a":"set","serial":true}.

Le module redémarre et le port apparaît sur la machine où il est branché. Pour le désactiver, envoyez {"t":"cfg","a":"set","serial":false} — y compris par le port COM lui-même, qui disparaît au redémarrage.

Aucun garde-fou côté module

L'application web refuse d'enregistrer une configuration sans canal de commande (Wi-Fi, COM ou BLE). Le module, lui, applique ce qu'il reçoit : un script qui coupe les trois le rend injoignable. Seul le reset d'usine (bouton BOOT maintenu 20 s) le récupère alors.

Paramètres de liaison

ParamètreValeurDétail

Contrôle de fluxAucunNi RTS/CTS, ni XON/XOFF.
DTRActifLe module n'émet vers l'hôte que si le port est déclaré ouvert (DTR). C'est le comportement par défaut de pyserial, PuTTY, miniterm ou Tera Term.
EncodageUTF-8Sans BOM. Les accents et € s'envoient tels quels.
Fin de ligneCR, LF ou CRLFChacun termine la commande : un terminal qui n'envoie qu'un retour chariot (PuTTY) fonctionne tel quel. Une ligne vide est ignorée.
TrameSTX … ETXForme alternative, reconnue en permanence : voir Tramage STX / ETX.
Longueur600 octetsMaximum par commande, fin de ligne ou STX/ETX non compris. Au-delà, la commande entière est rejetée : {"id":0,"err":"toolong"}.

Réponses1 par ligneObjet JSON terminé par CR LF, 512 octets au plus ; encadré par STX / ETX si la dernière commande reçue l'était.

Tramage STX / ETX pour les automates

En plus des lignes, le module reconnaît en permanence des commandes encadrées :

OctetHexRôle
STX0x02Début de trame. Tout reste d'une commande incomplète est jeté : le module repart proprement après un envoi interrompu (programme arrêté en cours d'écriture, câble débranché…).
JSON—La commande. Entre STX et ETX, les sauts de ligne sont de simples espaces : un JSON indenté sur plusieurs lignes est accepté.
ETX0x03Fin de trame : la commande est exécutée.
CR LF0x0D 0x0AFacultatifs après ETX (ignorés).
Octets échangés
→ 02 {"t":"ping","n":1} 03 0D 0A
← 02 {"id":0,"ev":"pong","n":1} 03 0D 0A

Les réponses adoptent le format de la dernière commande reçue sur le port : après une trame, elles sont encadrées (STX JSON ETX CR LF) ; après une ligne, elles redeviennent des lignes (JSON CR LF). Le JSON n'autorise aucun caractère de contrôle brut dans ses chaînes : STX et ETX ne peuvent jamais apparaître dans une commande valide.

Faut-il l'utiliser ?

Le lien USB détecte et corrige déjà les erreurs de transmission : le tramage n'ajoute pas de contrôle d'intégrité. Il apporte une délimitation explicite, pratique pour les automates qui parlent déjà STX/ETX, et une resynchronisation garantie. Pour un terminal ou un script simple, la ligne suffit.

Format d'une commande

Un objet JSON par ligne. Seul le champ t (type de commande) est obligatoire ; les champs inconnus sont ignorés. Les nombres sont des entiers JSON.

ChampTypeRôle
t requischaîneType : char, txt, key, seq, stop, mouse, ping, gpio, cfg, sec, name, pair.
identierModule visé dans une étoile : 0 (défaut) = ce module, 1 à 3 = esclave (voir Piloter une étoile). cfg, pair, sec et name restent locales.
mentierModificateurs ajoutés à la frappe (char, key, étapes de seq).

Masque des modificateurs champ m

BitValeurTouche
01Ctrl
12Maj (Shift)
24Alt
38Windows / Cmd (GUI)

Les bits se cumulent : Ctrl+Maj = 3, Ctrl+Alt = 5. Une ligne qui n'est pas du JSON valide renvoie {"id":0,"err":"json"} ; un t absent ou inconnu renvoie {"id":0,"err":"type"}.

Réponses

Chaque réponse est un objet JSON portant id — 0 pour ce module (ou le maître), 1 à 3 pour un esclave relayé — et un seul des discriminants suivants :

DiscriminantValeursExemple
st — étatbusy, ready{"id":0,"st":"busy"}
err — erreurvoir Codes d'erreur{"id":0,"err":"unmapped"}
ev — événementpong, gpio, cfg, sec, name, scan, pair, link, sys{"id":0,"ev":"pong","n":7}
Le port COM reçoit tout

Les réponses sont diffusées sur tous les canaux à la fois : le port COM reçoit aussi celles des commandes venues du Bluetooth, du Wi-Fi, du bouton BOOT ou d'une entrée GPIO. Aucune réponse ne porte de numéro de requête, sauf le pong (champ n) : filtrez sur le contenu.

Ce qui est acquitté, et ce qui ne l'est pas

  • char, key et mouse réussis ne renvoient rien ; seules leurs erreurs sont signalées.
  • txt et seq sont encadrés par busy puis ready (y compris après une erreur).
  • ping, gpio, cfg, sec, name et pair répondent par un événement.

Les commandes étant exécutées une à une, dans l'ordre, un {"t":"ping","n":N} sert de barrière de synchronisation : la réception de {"id":0,"ev":"pong","n":N} garantit que tout ce qui précède est terminé. C'est aussi la mesure de latence la plus simple.

Lisez le port en continu

Le module garde au plus 16 réponses en attente d'envoi et n'attend l'hôte que 20 ms. Si le port est ouvert sans être lu, les réponses suivantes sont perdues sans avertissement.

Commandes

Chaque commande est décrite avec ses champs, ses réponses et des exemples prêts à copier.

char taper un caractère

ChampTypeDescription
v requischaîneLe caractère. Seul le premier caractère est utilisé.
mentierModificateurs ajoutés (raccourcis).
 
→ {"t":"char","v":"é"}
→ {"t":"char","v":"c","m":1}      // Ctrl+C
→ {"t":"char","v":"T","m":1}      // Ctrl+Maj+T (la majuscule porte déjà Maj)
→ {"t":"char","v":"r","m":8}      // Win+R

Réponse : aucune si la frappe réussit. Erreurs : unmapped (caractère absent de la disposition AZERTY), empty (v vide), nohid (clavier désactivé).

La traduction en touches est faite par le module : la machine cible doit être réglée en AZERTY français (Windows ou Linux). Couverts : lettres, chiffres, ponctuation du clavier français, é è à ç ù, € £ ¤ µ § °, et les accents à touche morte â ê î ô û ä ë ï ö ü ÿ (deux frappes chacun). ^ ¨ ` ~ seuls sont tapés « touche morte + espace ». Les majuscules accentuées (É, À…) ne sont pas couvertes.

txt taper une chaîne

ChampTypeDescription
v requischaîneTexte UTF-8. \n tape Entrée, \t tape Tab, \r est ignoré.
 
→ {"t":"txt","v":"Réunion à 14h30\n"}
← {"id":0,"st":"busy"}
← {"id":0,"st":"ready"}
→ {"t":"txt","v":"Élan"}
← {"id":0,"st":"busy"}
← {"id":0,"err":"unmapped:U+00C9"}
← {"id":0,"st":"ready"}

Réponse : busy, puis ready une fois le texte tapé. Un caractère non couvert est sauté et signalé par unmapped:U+XXXX (son point de code) ; le reste du texte est tapé. Erreur : nohid.

Cadence : environ 16 ms par frappe, soit ≈ 60 caractères par seconde (deux frappes pour un accent à touche morte). Longueur : la ligne JSON complète ne dépasse pas 600 octets — environ 560 caractères ASCII, moins avec des accents (2 octets chacun). Découpez les textes longs en plusieurs txt.

→ {"t":"key","c":"Enter"}
→ {"t":"key","c":"F4","m":4}                  // Alt+F4
→ {"t":"key","c":"Escape","m":3}              // Ctrl+Maj+Échap
→ {"t":"key","c":"ShiftLeft","a":"down"}      // maintenir Maj…
→ {"t":"key","c":"ArrowDown"}                 // …sélectionner…
→ {"t":"key","c":"ShiftLeft","a":"up"}        // …relâcher
→ {"t":"key","c":"MediaVolumeUp"}

Réponse : aucune si la frappe réussit. Erreurs : unmapped (nom inconnu — un caractère simple comme "a" passe par char), nohid.

Six touches au plus peuvent être maintenues en même temps. Une touche maintenue le reste jusqu'à son up, un STOP ou la fin d'une seq : pensez à la relâcher.

seq séquences temporisées

Trois formes, selon le champ présent :

FormeSyntaxeEffet
Prédéfinie{"t":"seq","n":"alt_tab"}ctrl_alt_del (Ctrl+Alt+Suppr), ctrl_esc (Ctrl+Échap), alt_tab, alt_f4, win_d (Win+D).
Personnalisée{"t":"seq","s":[…]}Liste d'étapes exécutées dans l'ordre (ci-dessous).
Arrêt{"t":"seq","n":"stop"}Ancienne forme de stop, toujours acceptée.

Étapes d'une séquence personnalisée

ÉtapeEffet
{"tap":"a"}Un seul caractère → frappe du caractère ; deux caractères ou plus → touche nommée ("Enter", "F5"…). Un nombre est accepté ({"tap":1} tape 1). m facultatif.
{"wait":1000}Pause en millisecondes, interruptible par STOP (granularité 20 ms).
{"rep":3,"every":4000,"tap":"3"}Répète tap rep fois, avec every ms entre deux frappes (pas après la dernière). m facultatif.
 
→ {"t":"seq","s":[{"tap":"F5"},{"wait":2000},{"rep":5,"every":8000,"tap":"ArrowRight"}]}
← {"id":0,"st":"busy"}
← {"id":0,"st":"ready"}

Réponse : busy … ready. Erreurs : seq (nom inconnu, ni n ni s), unmapped (étape non couverte, la séquence continue), nohid. Toutes les touches sont relâchées en fin de séquence. Le tempo est tenu par l'horloge du module : la latence du lien ne déforme pas les délais. Pendant une séquence, les commandes suivantes attendent leur tour dans la file.

stop arrêt d'urgence, hors file

→ {"t":"stop"}
← {"id":0,"st":"ready"}

N'attend pas son tour : interrompt la séquence ou le texte en cours, vide la file des commandes en attente et relâche toutes les touches. Sur un maître, l'arrêt est aussi transmis à tous les esclaves (id ignoré). L'ancienne forme {"t":"seq","n":"stop"} reste acceptée. Les effets GPIO ne sont pas concernés : {"t":"gpio","a":"clr"} les arrête. Détails dans STOP, hors file.

mouse déplacement, molette, boutons

ChampTypeDescription
dx, dyentierDéplacement relatif (vers la droite / vers le bas si positif). Les grandes valeurs sont découpées en pas de ±127.
wentierMolette verticale (positif = vers le haut).
bchaîneBouton : left, right, middle.
achaîneAction du bouton : click (défaut), dbl (double-clic), down, up.

Un message fait soit un déplacement / une molette, soit une action de bouton : si dx, dy ou w est présent, b est ignoré.

→ {"t":"mouse","dx":120,"dy":-40}
→ {"t":"mouse","w":-3}                       // 3 crans vers le bas
→ {"t":"mouse","b":"left","a":"down"}        // glisser-déposer :

→ {"t":"mouse","b":"left","a":"up"}

Réponse : aucune si l'action réussit. Erreurs : mouse (bouton inconnu, message vide), nohid (souris désactivée).

ping test de liaison et barrière

→ {"t":"ping","n":12}
← {"id":0,"ev":"pong","n":12}
→ {"t":"ping","n":13,"id":1}                  // routé vers l'esclave 1
← {"id":1,"ev":"pong","n":13}

n est un entier libre (défaut 0), renvoyé tel quel. Utilisez un n différent à chaque appel pour associer chaque pong à son ping.

gpio entrées / sorties du module

ChampTypeDescription
pchaîneRepère de la broche : "o1" à "o4" (sorties), "i1" à "i4" (entrées), "BOOT" (bouton intégré, entrée). Majuscules acceptées ("O1") ; les réponses utilisent toujours la forme en minuscules. Absent : toutes les broches (read ou clr seulement).
achaîneread (défaut), set (niveau haut), clr (niveau bas), tgl (inverser), loop (clignotement autonome), pwm (PWM autonome). Écriture sur les sorties uniquement.
 
→ {"t":"gpio","p":"o1","a":"set"}
← {"id":0,"ev":"gpio","p":"o1","v":1}
→ {"t":"gpio","a":"read"}                     // 9 réponses, une par broche
← {"id":0,"ev":"gpio","p":"BOOT","v":0}
← {"id":0,"ev":"gpio","p":"o1","v":1}
  …
→ {"t":"gpio","p":"o3","a":"tgl","id":2}      // sortie o3 de l'esclave 2
← {"id":2,"ev":"gpio","p":"o3","v":1}
  • Sorties : v:1 = 3,3 V. Toutes à 0 au démarrage. {"t":"gpio","a":"clr"} sans p éteint toutes les sorties et arrête tous les effets (une réponse par sortie).
  • Entrées : résistance de rappel au 3,3 V, actives à l'état bas : v:1 = contact fermé vers la masse (bouton pressé). Chaque changement est signalé spontanément, après un anti-rebond d'environ 60 ms.
  • Erreur gpio : fonction GPIO désactivée, broche inconnue — y compris les anciens repères numériques "4"…"11" ou un p non textuel —, écriture sur une entrée, action inconnue, paramètre d'effet absent ou hors limites.

Repères et broches physiques pour le câblage

Les repères sont logiques : numérotés à partir de 1 dans chaque sens, indépendamment du numéro de GPIO de la puce. Une broche ajoutée par une future version prend simplement le repère suivant de son sens (o5, i5…) : les repères existants ne changent jamais.

Effets autonomes clignotement et PWM exécutés par la carte

Pour un changement d'état fréquent et répétitif, inutile d'envoyer une commande par transition : une seule commande lance l'effet, la carte visée l'exécute seule. Le lien radio ne transporte que deux réponses, au départ et à la fin.

ActionChampLimitesRôle
loopt_set requis10 ms à 24 hDurée de l'état haut, en millisecondes.
t_clr requis10 ms à 24 hDurée de l'état bas, en millisecondes.
nbentier ≥ 0Nombre de cycles (haut puis bas). 0 ou absent : sans fin.
pwmduty requis0 à 100Rapport cyclique, en %. 0 et 100 donnent un niveau fixe.
t_pwm0 à 24 hDurée en millisecondes. 0 ou absent : sans fin.
hz10 à 40 000Fréquence (défaut 1000). Résolution réglée automatiquement : 14 bits (16 384 pas) jusqu'à 2,4 kHz, puis dégressive jusqu'à 9 bits (512 pas) à 40 kHz.
 
→ {"t":"gpio","p":"o1","a":"loop","t_set":200,"t_clr":800,"nb":5}
← {"id":0,"ev":"gpio","p":"o1","v":1,"fx":"loop"}
  … 5 éclats de 200 ms, une seconde d'intervalle, sans aucune trame …
← {"id":0,"ev":"gpio","p":"o1","v":0,"fx":"loop","done":true}
→ {"t":"gpio","p":"o2","a":"pwm","duty":25,"t_pwm":3000,"id":2}   // sur l'esclave 2
← {"id":2,"ev":"gpio","p":"o2","v":1,"fx":"pwm","duty":25}
← {"id":2,"ev":"gpio","p":"o2","v":0,"fx":"pwm","done":true}     // 3 s plus tard
  • Une nouvelle commande interrompt la commande en cours : set, clr, tgl, loop ou pwm sur une sortie arrête son effet et applique la nouvelle consigne. read n'interrompt rien (sa réponse porte fx si un effet tourne). Une commande refusée (err:gpio) laisse l'effet en place.
  • Chaque sortie a son propre effet : les quatre sorties peuvent clignoter ou moduler en même temps, à des rythmes différents, sur chaque module de l'étoile.
  • Fin : quand nb cycles ou t_pwm sont écoulés, la sortie revient à 0 et la réponse porte "done":true. Un effet interrompu ne produit pas de done : la réponse de la nouvelle commande en tient lieu.
  • Charge : une seule tâche gère toutes les sorties et dort jusqu'à la prochaine échéance — deux réveils par cycle de clignotement, aucun pendant un PWM, produit par le matériel. Le clavier, la souris et les liaisons n'en sont pas ralentis.
  • Précision : le rythme est tenu par l'horloge de la carte, à la milliseconde près, indépendamment de la liaison.
  • Le stop clavier n'arrête pas les effets GPIO.

name nom convivial

→ {"t":"name","name":"Bureau"}
← {"id":0,"ev":"name","name":"Bureau","reboot":true}   // puis redémarrage
→ {"t":"name","id":2,"name":"Cuisine"}                  // maître : renomme l'esclave 2

19 octets au plus (au-delà, le nom est tronqué) ; "" rétablit le nom par défaut S3-KBD-XXYY. Le nom sert d'annonce Bluetooth et, pour un maître, de nom du réseau Wi-Fi : renommer ce module le redémarre. Renommer un esclave depuis le maître ne redémarre pas l'esclave. Erreur : id (esclave inconnu).

scan{"t":"pair","a":"scan"}busy, puis une ligne par module trouvé {"id":0,"ev":"scan","mac":"…","rssi":-60,"name":"…"}, puis {"id":0,"ev":"scan","done":true} et ready. Environ 4 s.
bind{"t":"pair","a":"bind","mac":"aa:bb:cc:dd:ee:ff","name":"Salle 2"} {"id":0,"ev":"pair","ok":true} + redémarrage : ce module devient maître, l'esclave reçoit le plus petit id libre. err:pair (appairage désactivé, adresse invalide ou déjà appairée, échec), err:full (3 esclaves).
unbind{"t":"pair","a":"unbind","id":2}pair ok + redémarrage. id absent ou 0 : toute l'étoile.
reset{"t":"pair","a":"reset"}pair ok + redémarrage : retour au rôle standard, passkey 000000, appairages effacés, nom conservé. Typiquement sur le port COM d'un esclave isolé.

L'action slave est interne : le maître l'envoie à un module vierge pendant bind. Ne l'utilisez pas.

File, cadence et STOP

Toutes les commandes — port COM, Bluetooth et Wi-Fi confondus — entrent dans une seule file de 16 places et sont exécutées une par une, dans l'ordre d'arrivée. Quand la file est pleine, la commande est refusée (err:busy) : attendez un pong avant d'envoyer de gros lots.

TempsValeur
Appui d'une touche5 ms
Repos après une frappe5 ms
Intervalle supplémentaire entre caractères (txt)6 ms
Granularité des pauses wait / every20 ms

STOP, hors file

{"t":"stop"} n'attend pas son tour : dès sa réception, avant même la file, le module interrompt la séquence en cours, vide la file, relâche toutes les touches et répond {"id":0,"st":"ready"}. Sur un maître, l'arrêt est aussi transmis à tous les esclaves.

La reconnaissance est exacte : seul un champ t valant "stop" (ou l'ancienne forme {"t":"seq","n":"stop"}) déclenche l'arrêt. Le mot « stop » dans un texte est tapé normalement : {"t":"txt","v":"stop"} tape bien « stop ».

Redémarrages

Ces commandes enregistrent un réglage puis redémarrent le module :

  • cfg set ;
  • sec passkey et sec wifi ;
  • name sur ce module (standard ou maître) ;
  • pair bind, unbind, reset ;
  • le bouton BOOT (5 appuis ou maintien 20 s).

La réponse part environ 300 ms avant le redémarrage. L'USB est alors réinitialisé : le port COM disparaît puis réapparaît quelques secondes plus tard — sous un autre numéro si les réglages USB ont changé. Fermez le port, attendez sa réapparition (en le recherchant par VID/PID), puis rouvrez-le.

Piloter une étoile

Un maître accepte au plus 3 connexions Bluetooth simultanées. Piloter le maître par le port COM n'en consomme aucune : les 3 restent disponibles pour les esclaves. C'est la configuration conseillée pour un hôte fixe (PC, Raspberry Pi).

  • Ajoutez "id":1 à 3 pour viser un esclave ; sans id, la commande s'exécute sur le maître.
  • cfg, pair, sec et name sont toujours traitées par le maître.
  • Les réponses d'un esclave sont relayées telles quelles, avec son id : {"id":2,"ev":"gpio","p":"i1","v":1}.
  • Esclave injoignable : {"id":2,"err":"nolink"}, et un événement link signale son retour.
  • Un esclave est destiné aux entrées/sorties. Son propre port COM (s'il est activé) le pilote localement ; {"t":"pair","a":"reset"} l'y libère de son maître.
→ {"t":"cfg","a":"get"}
← {"id":0,"ev":"cfg",…,"role":1,…,"slaves":[{"id":1,…,"up":1},{"id":2,…,"up":0}]}
→ {"t":"gpio","p":"o2","a":"set","id":1}
← {"id":1,"ev":"gpio","p":"o2","v":1}
→ {"t":"gpio","p":"o2","a":"set","id":2}
← {"id":2,"err":"nolink"}

Exemples

Python pyserial — détection, lecture continue, barrière

s3kbd.py
import json, threading, serial                     # pip install pyserial
from serial.tools import list_ports

VID, PID = 0x303A, 0x8161

def trouver_port():
    for p in list_ports.comports():
        if p.vid == VID and p.pid == PID:
            return p.device
    raise SystemExit("S3-KBD introuvable : le port COM est-il activé ?")

class S3KBD:
    def __init__(self, port=None):
        self.ser = serial.Serial(port or trouver_port(), 115200, timeout=0.1)   # DTR actif par défaut
        self.pongs = {}
        threading.Thread(target=self._lire, daemon=True).start()

    def _lire(self):                                   # lecture continue (voir « Réponses »)
        buf = b""
        while True:
            buf += self.ser.read(512)
            while b"\n" in buf:
                ligne, buf = buf.split(b"\n", 1)
                ligne = ligne.strip().strip(b"\x02\x03")  # CR final, et STX/ETX en mode tramé
                if not ligne:
                    continue
                msg = json.loads(ligne)
                ev = self.pongs.pop(msg.get("n"), None) if msg.get("ev") == "pong" else None
                if ev: ev.set()
                else:  print("←", msg)

    def envoyer(self, cmd, trame=False):
        ligne = json.dumps(cmd, ensure_ascii=False, separators=(",", ":")).encode("utf-8")
        if len(ligne) > 600:
            raise ValueError("commande > 600 octets : découpez-la")
        if trame:                                      # STX JSON ETX CR LF (voir « Tramage »)
            self.ser.write(b"\x02" + ligne + b"\x03\r\n")
        else:
            self.ser.write(ligne + b"\r\n")

    def attendre(self, n, delai=10):
        """Rend la main quand toutes les commandes précédentes sont exécutées."""
        ev = self.pongs[n] = threading.Event()
        self.envoyer({"t": "ping", "n": n})
        if not ev.wait(delai):
            raise TimeoutError("pas de pong")

kbd = S3KBD()
kbd.envoyer({"t": "txt", "v": "Bonjour, café à 5 € !\n"})
kbd.envoyer({"t": "char", "v": "s", "m": 1})        # Ctrl+S
kbd.attendre(1)
kbd.envoyer({"t": "gpio", "p": "o1", "a": "loop", "t_set": 200, "t_clr": 800, "nb": 5})
kbd.envoyer({"t": "stop"}, trame=True)

BIOS / UEFI entrer dans le setup au démarrage

La touche d'accès (F2, Suppr, F10…) doit tomber dans une fenêtre très courte : une séquence la répète, au tempo du module, et stop l'interrompt dès que l'écran du setup s'affiche. Ensuite, n'utilisez que des touches nommées : avant le système, la machine lit le clavier en QWERTY US (voir « Limites »).

→ {"t":"seq","s":[{"rep":40,"every":250,"tap":"F2"}]} // 10 s de F2
→ {"t":"stop"}                                        // setup affiché
→ {"t":"key","c":"ArrowDown"}                         // naviguer
→ {"t":"key","c":"NumpadAdd"}                         // + (pavé num.)
→ {"t":"key","c":"F10"}                               // enregistrer
→ {"t":"char","v":"y"}                                // confirmer

Terminal interactif

Tout terminal série convient : CR, LF et CRLF terminent tous une commande. Activez l'écho local pour voir ce que vous tapez :

  • PuTTY : Terminal → Local echo et Local line editing sur « Force on » ;
  • miniterm (fourni avec pyserial) : python -m serial.tools.miniterm COM7 115200 -e ;
  • Moniteur série de l'IDE Arduino : n'importe quelle fin de ligne sauf « Pas de fin de ligne » ;
  • Tera Term : Configuration → Terminal → écho local.

Limites et bonnes pratiques

  • Disposition : la machine cible doit être en AZERTY français. Les majuscules accentuées et les caractères absents d'un clavier français renvoient unmapped : rien n'est tapé au hasard.
  • BIOS / UEFI : le module se présente comme un clavier compatible démarrage (« boot »), mais avant le système la machine lit le clavier en QWERTY US. Utilisez les touches nommées (F1–F12, flèches, Enter, Escape, Delete, NumpadAdd / NumpadSubtract pour + / −) plutôt que char : un - AZERTY y donnerait « 6 ». Les lettres y, n, e, c, x sont au même endroit dans les deux dispositions. Évitez la souris et les touches média pendant le BIOS : elles peuvent y produire des frappes parasites.
  • Aucun chiffrement : le port COM est un canal physique de confiance. Quiconque accède à la machine hôte peut piloter le module.
  • Un seul port série : il n'existe que si le réglage serial est actif, et sert uniquement au protocole (pas de console de diagnostic).
  • Lecture continue du port, barrière ping avant les gros lots, relâchement des touches maintenues : les trois habitudes qui évitent les surprises.
  • Compatibilité : le même JSON fonctionne en Bluetooth (caractéristique CMD) et en Wi-Fi (une trame WebSocket par commande) : un script se porte d'un canal à l'autre sans modification du contenu.
